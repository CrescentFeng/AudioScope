# AudioScope 声音事件工作台

本页对应 v1.0 后的工作台增强开发，不替代原 v1.0 封板记录。
软件预测不是人工真值；未进行自有物理设备/房间认证。

## 启动与入口

日常使用请双击桌面 `AudioScope/打开AudioScope.command`。它会检查并按需启动本机 Docker Desktop、
恢复已有数据库和页面服务，验证页面、历史记录接口、模型哈希及一次测试推理，全部通过后才打开
`http://127.0.0.1:7862/`。重复双击不会启动第二套服务；不会改用其他端口、清空历史或关闭其他程序。
关闭启动终端不会停止后台容器。Docker 进程崩溃退出时由既有重启策略恢复；健康检查失败本身不等于自动重启，
下次通过一键入口打开时会尝试一次页面服务重启，失败则给出提示。

仅检查现状（不启动/重启服务、不打开浏览器）：

```bash
.venv/bin/python scripts/open_audioscope.py --check
```

只启动并验证（不打开浏览器）：

```bash
.venv/bin/python scripts/open_audioscope.py --no-open
```

最近一次诊断在 `runtime/startup/latest.json`，不记录数据库密码。电脑睡眠、Docker未运行或端口冲突时，
直接点击收藏的网址仍可能无法连接；请用一键入口恢复。项目路径移动、数据卷丢失、模型损坏等问题会停止并提示，
不承诺任意故障下零失败。首次 Docker 权限和协议提示需用户自行完成；没有修改登录项或全局代理。

以下为开发调试的手动启动方式（不建议作为日常入口）。在项目根目录运行：

```bash
.venv/bin/python -m audioscope.launch
```

默认尝试本机 7861–7870 中的空闲端口，以终端实际打印地址为准。不会关闭占用端口的其他程序。
项目 `.env` 有数据库配置时使用 PostgreSQL；离线运行可加 `--local-history`，明确使用 SQLite。
两者的历史不会自动互相复制。旧 `l4_app.py` 保留用于原版演示和文件流模拟。

正式 Python 容器（需要 Docker 正常运行及本地模型/数据）：

```bash
docker compose build api
AUDIOSCOPE_API_PORT=8002 AUDIOSCOPE_DEMO_PORT=7862 docker compose --profile demo up -d --no-build api demo
```

工作台 `http://127.0.0.1:7862`；分析 API `http://127.0.0.1:8002/docs`。
显式指定端口会覆盖旧 `.env` 中的端口配置。本次验收发现 8000 和 7860 已被其他程序占用，未终止它们。
这是一套 Python/ONNX/CLAP 服务，不是旧的 PHP 只读兼容 API。
数据库、API、工作台宿主机端口绑定本机；不要直接改为公网发布。本版没有多用户认证。

## 第一次使用

1. 点击“试用示例音频”，再点“2 · 开始分析”。模型和检测偏好已设好，通常不必展开“高级设置”。
2. 检查中文摘要和时间轴。示例约 119 秒，结果数量依模型和工作点变化，不是固定答案。
3. 点击事件表中的任一行回听；片段包含前后各 0.5 秒上下文，音频边界处自动裁切。
4. 如需评测，展开“专业工作台”，在“参考与版本对照”勾选内置示例参考，点击对照。
5. 如需检索，展开“专业工作台”，在“文本检索”输入“人声并伴随流水”。
6. 在“历史与导出”下载 JSON/CSV。JSON 保留模型哈希、阈值和复核版本，CSV 标明事件来源。

## 正确理解结果

- 最高分是事件内帧得分峰值；平均分是片段内均值。二者都不是经过保证的正确率。
- `unknown` 是待确认片段，不代表静音，不保证发现所有未知声音，也没有识别出一个新类别。
- event-F1 同时受类别、起止边界和事件数量影响；segment-F1 衡量时间段内是否存在声音。
- `overall`、`short_event`、`class_balanced` 是验证集选择的不同工作点，没有对所有音频通用的最优选项。
- 模型之间的差异不等于谁更准确。完整参考标注对照只能说明这份音频上的表现。
- 原始 v1.0 模型仍可选择；默认边界优化版与基线使用相同神经网络权重/ONNX，修改的是事件解码配置。

## 人工复核与参考标注是两件事

“人工复核”允许改类别、起止时间，新增漏检或删除误报。必须明确确认后保存；每次追加新版本，
不会覆盖模型预测，也不会自动加入训练数据。其他会话先保存时，本会话会收到版本冲突提示。
自动测试产生的记录标记为 `software_verification_fixture`，不是人工标注。

用于计算指标的参考 JSON 需要独立提供；必须对应完全相同的音频 SHA-256，并明确是完整标注：

```json
{
  "audio_sha256": "替换为原始WAV的SHA-256",
  "source": "human_reference",
  "complete": true,
  "events": [{"label": "speech", "onset_s": 1.0, "offset_s": 2.5}]
}
```

此格式只举例，不能直接当作示例音频真值。内置参考来自已有 DESED 标签，并先重建波形验证一致性。
空事件列表表示已确认整段没有目标声音，不表示“还没标完”。不能用部分标注计算完整准确率。

## 两种检索

类别查询支持项目十类声音及 unknown 的中英文别名；“同时”“伴随”求预测区间交集。
目前不支持否定条件，不会将未知文本自动猜成某一类。

CLAP 开放描述使用本地英文文本编码器，例如 `metal clanging` 或 `a person talking`。
每次最多 5 分钟，10 秒窗口、5 秒步长；首次建立索引较慢，重复查询复用单条音频的内存索引。
中文开放描述暂不支持，模型不自动联网下载。
返回的是相似候选，不是精确检测边界；即使目标声音不存在，也可能返回候选。
现有评测只覆盖十类固定英文查询，不能宣称理解任意声音描述。

## 隐私、保留与故障处理

- 音频限制：PCM/浮点 WAV，最长 30 分钟、最大 100 MiB，拒绝 NaN/Inf。
- 默认数据库保存结果和哈希，不永久保存上传原音频；Gradio 上传/回听缓存按 24 小时 TTL、每小时清理。
- 勾选保留后，音频存入 `runtime/workbench/audio/`；这是显式的长期本机存储，不承诺自动删除。
- 默认未保留的历史任务仍可查看结果；回听或 CLAP 需重新关联字节完全相同的 WAV。
- 导出临时目录按 24 小时 TTL 在启动和导出时清理；历史结果和复核版本不随缓存清理删除。
- 浏览器“拒绝连接”：确认进程/容器已运行，按终端实际端口访问；不是重新上传音频就能解决。
- “文件哈希不一致”：不要用转码、剪辑后的音频关联旧任务；应创建新分析。
- 容器内模型缺失：检查只读挂载的 `artifacts/` 和 `data/pretrained/`，不会自动下载替代模型。
- 参考标签、测试音频、自动复核记录都不自动进入训练；未来训练导出需要单独审核与划分。

## 可重复验收

```bash
.venv/bin/python -m pytest -o addopts='' -q
.venv/bin/ruff check src tests scripts
NO_PROXY=127.0.0.1,localhost .venv/bin/python scripts/verify_deployment.py
```

最后一条会提交项目示例音频、建立测试历史和复核夹具；需要本机 PostgreSQL 和上面的两个容器入口。
报告为 `reports/generated/workbench/container-verification.json`。浏览器渲染与表格点击仍需单独核验，
不能把 API 测试通过当成所有页面交互已通过。
